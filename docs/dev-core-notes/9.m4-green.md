## The journal_digest refactor (product decision)

The raw journal (696 B) + seal (256 B) in one instruction exceeded Solana's 1232-byte
transaction limit. Rather than split the transaction or stuff the journal in an
account, the coordinator now takes `journal_digest: [u8; 32]` directly. The prover
service computes `sha256(journal)` off-chain and passes the digest.

This is strictly better for the product: the raw journal should never be on-chain
(it's the circuit output), the digest is all the verifier needs (the router builds
the claim digest from it), and the transaction stays small. The `#[instruction(...)]`
macro attribute also had to be updated to match — a stale `journal: Vec<u8>` there
caused an out-of-memory error because Anchor tried to deserialize the full vec.

## The devnet deployment lessons (hard-won)

Getting a working verifier router on devnet was the bulk of M4's effort. Five
non-obvious requirements, each of which blocked progress until resolved:

1. **The router must be initialized.** The `6JvFf...` program (from the ee41593
   local checkout) exists on devnet but was never initialized — its router state
   PDA doesn't exist. We deploy our own router and call `initialize`.

2. **declare_id must match the deployment address for every program in the CPI
   chain.** `DeclaredProgramIdMismatch` (0x1004) fires when a program's baked-in
   `declare_id!` differs from where it's deployed. This applies transitively:
   coordinator → router → groth16, all three must be consistent. Patch the
   `declare_id!` in source, clean-rebuild (delete cached `lib*.rlib`), redeploy.

3. **The coordinator's `verifier_router::ID` comes from the crate.** The coordinator
   CPIs into the router using `verifier_router::ID` — a const from the dependency
   crate. Changing the router's deployment address means patching the crate source
   in the cargo git checkout and force-rebuilding the coordinator so it links the
   new const.

4. **add_verifier requires the router PDA to be the groth16 upgrade authority.**
   The router's `add_verifier` checks
   `verifier_program_data.upgrade_authority_address == Some(router.key())`. You
   cannot set a PDA as upgrade authority normally (PDAs can't sign), but
   `solana program set-upgrade-authority --skip-new-upgrade-authority-signer-check`
   does it. Once the router PDA owns the groth16 program, the program is
   permanently locked under the router (can't take authority back).

5. **verifier_entry is permanent and keyed by selector.** The verifier_entry PDA
   is `[b"verifier", selector]` and stores the registered groth16 address forever
   (no remove_verifier; only emergency_stop). If you register the wrong groth16
   address for a selector, you must deploy a *fresh router* to get a clean
   verifier_entry namespace. We burned through several groth16 deployments learning
   this; the final clean set above was deployed fresh and consistent in one pass.

## What carries to M5

- Full on-chain nullifier binding (still using the `authorized_prover` constraint;
  risc0-serde on-chain decode deferred).
- Fully stateless proving service (journal in request body).
- A devnet deployment script that does the full consistent sequence in one shot,
  so this never has to be rediscovered by hand.

## The honest status

The full confidential-compute stack — shielded predicate on Logos → Groth16 wrap →
Solana verification → consumer action — is now demonstrated on a public validator,
not just litesvm. The secret was a private witness in the circuit, absent from the
journal, absent from the seal, and absent from every byte of the devnet transaction.
The explorer link is the artifact.
