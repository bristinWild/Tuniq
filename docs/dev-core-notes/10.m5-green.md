# 10 - M5 GREEN: cryptographic nullifier binding + accelerators (already true)

M5 closes both halves of its scope. The nullifier binding half is new code,
covered in the previous commit (`afd10a0`) and verified by the litesvm test:
the coordinator now decodes `new_nullifiers[index]` directly from the
proof-committed journal on-chain, and the `authorized_prover` trust shortcut
is gone entirely.

The accelerator half closes by a different route: **it's already true, and
was already true before M5 started.** This note records why, so the roadmap
item isn't left looking unaddressed.

## What the roadmap item asked for

> Route `sol_sha256` (and other crypto syscalls) to RISC Zero accelerators.
> Add signature-verification syscall support.
> Re-measure proving cost with crypto syscalls vs. baseline.

This was written speculatively at M4, anticipating that future predicates
might need crypto-heavy operations and that we'd need to wire those into
RISC Zero's accelerated precompiles ourselves.

## What's actually in the circuit

`check_balance_over_threshold` (`predicate-engine/src/check.rs`) does exactly
one thing: `subject.account.balance >= threshold`. A `u128` comparison. No
hashing, no signatures, nothing accelerator-shaped, in *our* code.

But our guest doesn't run in isolation - it's built on `nssa_core`
(`logos-execution-zone` v0.2.0-rc3), and `nssa_core` itself is full of
cryptographic hashing: commitments, nullifiers, account hashing, encryption
key derivation. Every one of these goes through:

```rust
use risc0_zkvm::sha::{Impl, Sha256 as _};
```

This import appears in `commitment.rs`, `account.rs`, `nullifier.rs`,
`encryption/mod.rs`, and `program.rs` - the full surface of cryptographic
operations the privacy-preserving circuit performs. `risc0_zkvm::sha::Impl`
is RISC Zero's own accelerated SHA-256 implementation: it's not an external
"patched crate" that needs opting into, it's the **SHA-256 precompile circuit
built into `risc0-zkvm` itself**, exposed as the canonical hashing API for
zkVM guests.

In other words: the moment our guest links against `nssa_core` - which it
must, to do anything privacy-preserving at all - every commitment computation
and every nullifier derivation already runs through the SHA-256 accelerator.
There is no unaccelerated path to route away from.

## "Re-measure vs baseline" - there is no baseline

The third bullet asked to compare crypto-syscall-accelerated proving cost
against a non-accelerated baseline. For that comparison to mean anything,
there would need to be a *real* unaccelerated variant of the circuit we could
swap in. There isn't one, and there's no reason to ever build one:

- `nssa_core` is the privacy framework. Un-patching its SHA-256 calls would
  mean either forking it or reimplementing commitment/nullifier logic
  ourselves - strictly worse on every axis (slower, divergent from the
  audited LEZ stack, more code to maintain).
- The M0–M5 proving times we've already measured (≈9.4s for the full
  shielded predicate, Experiment 1's ≈314 cycles/instruction baseline) **are**
  the accelerated numbers. They always have been. There's nothing to
  re-measure against.

## Signature verification - deferred, correctly

`check_balance_over_threshold` has no signature checks; nothing in the
current circuit needs `ed25519`/`secp256k1` precompiles. This stays an M6+
concern: if a future predicate (M6 opcode/syscall coverage, M7 flagship demo)
needs signature verification inside the guest, that's the point to evaluate
RISC Zero's `k256`/`ed25519-dalek` accelerated forks - gated correctly behind
the `unstable` feature flag per RISC Zero's current precompile docs, since
those forks don't yet provide constant-time guarantees suitable for
private-data signing. Pulling this in now, with nothing that needs it, would
be unused complexity and an unnecessary `unstable`-flag dependency.

## M5 - full closure

- ✅ **Nullifier binding**: on-chain `journal_decode` module, `store_journal`
  + updated `verify_predicate`, `authorized_prover` removed. litesvm green
  (`afd10a0`).
- ✅ **Accelerators**: SHA-256 acceleration is structural, inherited from
  `nssa_core::risc0_zkvm::sha::Impl` for every commitment/nullifier hash in
  the circuit. No code change needed; no unaccelerated baseline exists to
  compare against.
- ⬜→carried **Signature verification precompiles**: correctly deferred to
  M6+, when a predicate that actually needs signatures is in scope.

**Done when** (per the roadmap): "the nullifier binding is cryptographic (not
key-based), and a crypto-adjacent predicate proves within acceptable cost and
time." Both are satisfied - the nullifier binding is cryptographic, and the
circuit's crypto-adjacent operations (commitments, nullifiers) already prove
at the accelerated cost they've always proven at.

## What carries to M6

- Devnet redeployment of the M5 coordinator (store_journal +
  trustless verify_predicate) - M4's devnet tx used the pre-M5 signature.
- Opcode/syscall coverage work, including evaluating signature-verification
  precompiles if a target predicate needs them.
