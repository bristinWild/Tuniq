# 11 - M5 devnet redeploy: parked on a proving-stack version skew

The M5 milestone (cryptographic nullifier binding) is **green in litesvm** and
committed (`afd10a0`). This note records the state of the *devnet
demonstration* of M5 - a carried item from the roadmap - which is parked, not
green, and explains precisely why, so it can be picked up cleanly later.

## What M5 actually requires (done)

The milestone is the trustless nullifier binding itself: the coordinator
decodes `new_nullifiers[index]` directly from the proof-committed journal
on-chain, removing the `authorized_prover` trust shortcut. This is proven by
the litesvm integration test `verify_and_forward_to_consumer`, which runs the
full chain (store_journal → verify_predicate → router CPI → groth16 pairing →
consumer CPI) against real artifacts and passes. That test is the M5 gate, and
it is green.

## What the devnet redeploy is (a demonstration, not the gate)

M4 demonstrated the *pre-M5* coordinator on a public validator. The natural
follow-on is to demonstrate the *M5* coordinator (with `store_journal` + the
new `verify_predicate` signature) on devnet too. This is a demonstration of
already-proven code on public infrastructure - valuable, but not the milestone.

## The blocker: a proving-stack version skew (not a code bug)

The M4 proof (June 9) verified on devnet. The new proof (regenerated today)
does not - against either the original `8RPusmPr…` verifier or the freshly
rebuilt `EZxA5G…` one. Everything statically inspectable matches:

- The Groth16 verifying key (`vk.rs`) is byte-identical to what
  `risc0-groth16 3.0.4` expects (confirmed: the on-chain bytes are the same
  ALPHA/BETA/GAMMA/DELTA/IC constants, big-endian).
- `ALLOWED_CONTROL_ROOT` (`a54dc85a…`) and `BN254_IDENTITY_CONTROL_ID`
  (`c07a6514…`) are **identical** between `risc0-circuit-recursion` 4.0.2 (what
  the verifier was originally built against) and 4.0.4 (what the prover uses) -
  so the version bump we tried was a non-factor.
- The instruction data reaching the verifier is correct: right selector, right
  `image_id` (`cc90d2a1…` LE-word form of `a1d290cc…`), right `journal_digest`
  (`b3d31aea…`), and `pi_a` is a valid point on BN254 (`y² = x³ + 3` holds).

Since the *verifier* parameters and the *instruction encoding* are both
correct, the mismatch is in the **proof's embedded public inputs** - which are
fixed by the proving environment (the r0vm recursion proving key + the
`v2025-04-03.1` Groth16 Docker container), not by the on-chain program or the
client. The working M4 proof was produced by the snapshot droplet's *original*
risc0 stack; today's proof was produced after a fresh `rzup install` pulled
`r0vm 3.0.5`. The most probable cause is that the recursion control root baked
into today's r0vm differs from the one the on-chain verifier's `vk.rs` +
control constants were bootstrapped for. The Rust crate checksums match, but
r0vm's proving key is a separate artifact and was not pinned.

## What carries to M6 (to unblock the devnet demo)

- **Pin the proving stack end-to-end.** The decisive next step is to confirm,
  on the prover host, the control root embedded in the succinct receipt
  (before the Groth16 wrap) and check it equals the verifier's
  `ALLOWED_CONTROL_ROOT` (`a54dc85a…`). If it differs, the r0vm / circuit
  version that produced the receipt is the skew; align it to the verifier's
  bootstrap version (or re-bootstrap `vk.rs` from the current stack and
  redeploy the verifier).
- **Codify a reproducible prover image.** The recurring source of churn across
  M4/M5 has been the proving environment drifting between sessions
  (host-flag cross-compile breaks, fresh `rzup install` pulling new keys). A
  pinned Docker image or a locked `rzup` toolchain version recorded in-repo
  would make the seal reproducible and the devnet demo a one-shot.
