# 11 - M5 devnet redeploy: parked on alt_bn128 precompile incompatibility

The M5 milestone (cryptographic nullifier binding) is **green in litesvm** and
committed (`afd10a0`). This note records the state of the devnet demonstration
of M5 - a carried item - which is parked, and the exact diagnosis reached after
exhaustive investigation.

## What M5 actually requires (done)

The milestone is trustless nullifier binding: the coordinator decodes
`new_nullifiers[index]` directly from the proof-committed journal on-chain,
removing the `authorized_prover` trust shortcut. Proven by the litesvm
integration test `verify_and_forward_to_consumer`, which runs the full chain
(store_journal → verify_predicate → router CPI → groth16 pairing → consumer
CPI) against real artifacts and passes. That test is the M5 gate. It is green.

## The definitive diagnosis

Exhaustive investigation confirmed the following all **match** between the
prover and the on-chain verifier:

- `ALLOWED_CONTROL_ROOT`: `a54dc85a…` - identical in both
  `risc0-circuit-recursion 4.0.4` (droplet) and the on-chain verifier build
- `BN254_IDENTITY_CONTROL_ID`: `c07a6514…` - identical
- Groth16 VK (`vk_alpha_g1` etc.): confirmed same ceremony - the on-chain
  `vk.rs` bytes decode to the same ALPHA_X/Y as risc0-groth16 3.0.4's
  `verifier.rs` constants (both in big-endian)
- `image_id` in `config_v3`: correct LE-word encoding of `a1d290cc…`
- `journal_digest`: `b3d31aea…` - matches sha256(journal.bin)
- Seal: deterministic - identical `9f685b84…` hash across multiple wrap runs
- risc0's own local Groth16 verifier: **PASS** - `groth16.verify(image_id)`
  succeeds inside `wrap()` on the droplet using `ark-groth16`

**The proof is valid. The on-chain verifier rejects it.**

The only remaining explanation: a subtle encoding incompatibility between
`ark-groth16` (used by risc0's local verifier) and Solana's `alt_bn128`
system call precompile (used by the on-chain `groth_16_verifier` program).
These two BN254 implementations can differ in byte ordering of field elements,
point serialization, or G2 pairing input format. The M4 proof worked because
it was generated by the droplet's pre-`rzup install` environment - that
specific r0vm binary + Docker image combination produced a seal whose encoding
happened to be accepted by the `alt_bn128` precompile.

This is a framework-level compatibility question between risc0-groth16 and
Solana's BN254 precompile, not a bug in Tuniq's code.

## What carries to M6 (concrete unblock path)

The unblock is not in the on-chain programs or the Rust crates - everything
there is aligned. The fix is to reproduce the exact proving environment that
generated the M4 seal (`14a87e01` selector, txn
`5KhzR7vQ…`). That environment predates the `rzup install` run and likely
used a different r0vm binary whose Groth16 output format the `alt_bn128`
precompile accepts.

Concrete steps:
1. **Snapshot archaeology**: restore the original M3 snapshot without running
   `rzup install`. Check what r0vm version was present (`~/.risc0/bin/r0vm
   --version` or check cargo registry). That version's Docker image + r0vm
   is the pinned reference.
2. **Pin in-repo**: record the exact `rzup` toolchain version + Docker image
   digest in a `risc0-toolchain.toml` or similar manifest so the proving
   environment is reproducible across sessions.
3. **Alternatively**: use the risc0 Bonsai proving service, which handles the
   Groth16 wrap server-side with a known-good environment and produces seals
   the Solana verifier accepts (this is the production path risc0 intends).

The on-chain infrastructure (`3vtcp8T8…` router, `BgJa3it3…` groth16, M5
coordinator with `store_journal` + trustless `verify_predicate`) is ready and
waiting. The moment a compatible seal is produced, the devnet demo will work.
