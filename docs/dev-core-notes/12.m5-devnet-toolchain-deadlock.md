# 12 - M5 devnet redeploy: parked on a toolchain-version deadlock

This note supersedes the "park" reasoning in note 11 with the **final** root
cause found after attempting the redeploy from a clean (pre-`rzup`) snapshot.
M5 itself is unchanged: **litesvm-green, committed (`afd10a0`)**. What is parked
is the *devnet demonstration* of the M5 coordinator. M4's devnet demonstration
(the pre-M5 coordinator) remains live and finalized - see below.

## TL;DR

Two independent, compounding blockers, both **external to Tuniq's code**:

1. **Solana toolchain deadlock** - the coordinator can no longer be deployed to
   devnet from this machine. Agave 4.0 compiles the program but emits an sBPF
   version devnet's loader rejects (`Detected sbpf_version required by the
   executable which are not enabled`). Every Agave ≤ 3.0 toolchain produces
   devnet-compatible sBPF but ships Rust 1.84, which cannot compile a
   transitive dependency (`block-buffer 0.12.0`) that requires edition 2024
   (Rust ≥ 1.85). No released Agave version bridges the gap (3.1/3.2 don't
   exist; `--arch v0` on 4.0 is still rejected).

2. **Groth16 / alt_bn128 proof-acceptance** - even with a fresh, fully
   version-aligned (risc0 3.0.5) router + verifier deployed, the on-chain
   `alt_bn128` pairing rejects the seal, although risc0's own local
   `ark-groth16` verifier accepts it (`Groth16 verify: PASS` on the prover
   host). All public-input constants match (ALLOWED_CONTROL_ROOT `a54dc85a…`,
   BN254_IDENTITY_CONTROL_ID `c07a6514…`, the VK, image_id, journal_digest).
   The seal is deterministic. The M4-era verifier (`8RPusmPr…`, built at risc0
   3.0.2/3.0.3) DID accept a 3.0.5 seal; freshly-built 3.0.5 verifiers do not.

The two interact: we could route around blocker 2 by pointing the coordinator
back at the original `CfAo7ygm…` router + `8RPusmPr…` verifier (which accepted
M4's 3.0.5 seal), but doing so requires **redeploying the coordinator** with
that router id baked in - which blocker 1 prevents. The currently-deployed
coordinator has `3vtcp8T8…` baked in, routing to the 3.0.5 verifier that
rejects the seal.

## Snapshot archaeology result

Restored the original pre-`rzup` DigitalOcean snapshot (no r0vm, no rzup, no
artifacts). Confirmed: the prover Cargo.lock there still pins risc0-zkvm 3.0.5
and the Groth16 Docker image is still `risczero/risc0-groth16-prover:v2025-04-03.1`.
**There was never a different proving stack** - M4's working seal came from this
same 3.0.5 + Docker setup. So blocker 2 is not "the proving environment
drifted"; it is specifically that a verifier *binary built at 3.0.2/3.0.3
accepts 3.0.5 seals while one rebuilt at 3.0.5 does not* - a
build-time/precompile-encoding interaction in the boundless `ee41593` verifier,
not a Tuniq bug.

## The unblock path (any ONE of these closes it)

1. **A bridging Solana toolchain** - an Agave release with Rust ≥ 1.85 that
   still emits devnet-accepted sBPF. When one ships, rebuild the coordinator
   with `verifier_router::ID = CfAo7ygm…`, redeploy, and run the client against
   `CfAo7ygm…` + `8RPusmPr…` (the M4-era verifier that accepts 3.0.5 seals).
   This is the lowest-effort path - no new proofs or ceremonies needed.
2. **Pin `block-buffer ≤ 0.10.4` in the lockfile** so an Agave ≤ 3.0 toolchain
   (devnet-compatible sBPF) can compile. Attempted this session; needs a clean
   resolver pass rather than hand-editing `Cargo.lock`. If it resolves, same
   redeploy-against-`CfAo7ygm…` plan as (1).
3. **Bonsai for the Groth16 wrap** - risc0's managed proving service produces
   seals the `alt_bn128` precompile accepts; this sidesteps blocker 2 entirely
   and is risc0's intended production path. Then deploy against the 3.0.5
   `BgJa3it3…` verifier the coordinator already points at - still needs blocker
   1 resolved to redeploy, OR keep the current coordinator as-is (it already
   points at the 3.0.5 stack) and only the seal source changes.
4. **Devnet enables sBPF v2** - removes blocker 1 outright; deploy the Agave
   4.0 build directly.
