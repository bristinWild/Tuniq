## Two non-obvious lessons - record them to avoid re-discovering

### 1. pi_a must be pre-negated by the caller

`verify_groth16` (the internal fn) has this doc comment:
> "The proof's `pi_a` element is expected to be negated."

The `verify` instruction does **not** negate internally. The caller must supply a
BN254 G1 negated pi_a: `(x, y) → (x, Q - y)` where Q is the BN254 base field
modulus. Passing the raw seal bytes (un-negated pi_a) produces a `VerificationError`
that looks like a wrong proof but is actually a wrong input encoding.

The helper used in the test (and needed by any caller of verify_predicate):
```rust
fn negate_g1(pi_a: &[u8; 64]) -> [u8; 64] {
    const Q: [u8; 32] = [
        0x30,0x64,0x4e,0x72,0xe1,0x31,0xa0,0x29,
        0xb8,0x50,0x45,0xb6,0x81,0x81,0x58,0x5d,
        0x97,0x81,0x6a,0x91,0x68,0x71,0xca,0x8d,
        0x3c,0x20,0x8c,0x16,0xd8,0x7c,0xfd,0x47,
    ];
    let mut out = [0u8; 64];
    out[..32].copy_from_slice(&pi_a[..32]);
    let y = &pi_a[32..64];
    let mut neg_y = [0u8; 32];
    let mut borrow: i16 = 0;
    for i in (0..32).rev() {
        let diff = Q[i] as i16 - y[i] as i16 - borrow;
        if diff < 0 { neg_y[i] = (diff + 256) as u8; borrow = 1; }
        else         { neg_y[i] = diff as u8;          borrow = 0; }
    }
    out[32..64].copy_from_slice(&neg_y);
    out
}
```

### 2. image_id must be passed as little-endian bytes per word

`image_id.txt` stores `PRIVACY_PRESERVING_CIRCUIT_ID: [u32; 8]` as 8 × 8 big-
endian hex chars (e.g. `a1d290cc...`). The verifier expects each u32 word as
**little-endian bytes** - confirmed by `my_proof_test.rs` using `val.to_le_bytes()`.

Parsing the hex naively as 32 consecutive bytes gives the wrong claim digest and
a silent `VerificationError`. Correct parse:

```rust
let image_id: [u8; 32] = (0..8usize)
    .flat_map(|i| {
        let w = u32::from_str_radix(&img_hex[i*8..(i+1)*8], 16).unwrap();
        w.to_le_bytes().to_vec()
    })
    .collect::<Vec<u8>>()
    .try_into()
    .unwrap();
```

This applies everywhere image_id is passed to the verifier: the test, the proving
service wrapper, any client that calls coordinator::initialize.

## Program setup - what the test established

### INITIAL_OWNER bypass via `set_account`

`verifier_router.so` is compiled with `INITIAL_OWNER = 11111...1` (system program)
when the env var is not set. Calling `router::initialize` requires signing with the
system program, which is impossible in a test. The bypass:

```rust
// Seed VerifierRouter directly - no initialize instruction needed.
svm.set_account(
    router_state_pda,
    Account { data: discriminator + borsh(Ownership), owner: router_id, ... }
);
svm.set_account(
    verifier_entry_pda,
    Account { data: discriminator + borsh(VerifierEntry), owner: router_id, ... }
);
```

Anchor account discriminators: `sha256("account:TypeName")[0..8]`.

### declare_id vs keypair address

The `.so` binary baked with `declare_id!("6JvFf...")` must be loaded at that exact
address in litesvm - not at the keypair file's address. The ee41593 checkout used
`declare_id!("6JvFf...")` for verifier_router and `"THq1q..."` for groth_16_verifier.
Build those `.so` files with:

```bash
cd ~/.cargo/git/checkouts/risc0-solana-1c84ab93fd21abb4/ee41593/solana-verifier
INITIAL_OWNER=11111111111111111111111111111111 anchor build --no-idl --ignore-keys
```

### journal_digest = sha256(journal_bytes)

Confirmed: the router passes `journal_digest` straight to `groth_16_verifier`, which
builds the claim digest internally via `hash_claim(image_id, journal_digest)`. The
coordinator computes: `hashv(&[journal.as_slice()]).to_bytes()` - plain sha256.

## What M2 starts with

- The nullifier binding check was removed for M1 (`NullifierNotInJournal`). The
  risc0-serde encoding wraps the nullifier in word-aligned framing, so a substring
  scan on the raw journal bytes fails. The tighter bind (decode the journal on-chain
  to extract `new_nullifiers` precisely) is M2 integration work.
- The `journal_contains_nullifier` function and `NullifierNotInJournal` error code
  are dead code in `lib.rs` - remove or implement in M2.
- The coordinator's `emit!(PredicateVerified)` event fires on success - a consumer
  program can listen for this or read the spent-nullifier PDA as the trusted signal.
- Next product slice: wire the coordinator to an actual consumer program that acts
  on the verified result (the M1 definition of "done").
